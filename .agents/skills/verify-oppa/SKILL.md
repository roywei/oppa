# Verify OPPA

Each drive in this skill's helper exercises one feature the way the owner reaches it and checks what proves it works. It runs on the built binary against a throwaway instance. A passing test is not a drive, and a drive on the owner's own instance is never allowed.

## Launch

```sh
.agents/skills/verify-oppa/scripts/oppa-verify launch            # --agent codex to use Codex
```

It builds `target/debug/oppa` and copies it into the instance's `bin/`, creates an instance under the system temp directory with `oppa init --access read`, so no drive reaches the owner's accounts unless it sets more, and prints the commit it built from and the `PATH`, `OPPA_HOME` and `OPPA_PRIVATE_DIR` to export if you want to run `oppa` commands yourself. Every drive and command on the instance runs that copy, so a later build in the checkout never changes the binary under a running drive; to test a newer build, launch again. Each grade records the commit as `source`. The helper remembers that instance for the commands below. Launch a new instance for each verification session.

## Doctor

`oppa-verify doctor` runs `oppa doctor` on that instance with no model request and fails if any check is not ready. Run it before the first drive and after any failure. Doctor does not prove the harness is signed in; the first chat turn does.

## Replay

`scripts/oppa-replay` replays recorded exchanges (E-1) and grades the replies (E-5). A case is one JSON file: the requirement rows it bears on (B-1 to B-10), the earlier messages with their authors and, for the assistant's, their delivery state, the owner's message to replay, the truth (what the person said or wanted next; their correction is the truth), and optional assertions (`silent`, `includes`, `excludes`, `retrieves`). The case's id names its result files (lowercase letters, digits, `-` and `_`); the owner's and people's ids are as `config.toml` has them, and a history author may also be a sender the host never identified, stored as `<channel id>:<handle>`, who stays unregistered in the replay as in the original. The file's docstring shows the shape; a case with any other shape is refused before anything runs.

```sh
oppa-replay draft --conversation <id> --at <seq> --out case.json   # from the instance in OPPA_HOME, read-only
oppa-replay run cases/*.json --out <new results folder>
```

`draft` opens the store read-only with SQLite itself (never `oppa`, which would migrate it), takes only a message the owner sent through a channel (a schedule slot, a task result or a console turn carries an authority of its own that a replay through a channel would change), keeps each assistant message's outbox state as of the replayed message (an outgoing message is stored before it is delivered; only its latest state is kept, so one confirmed sent after the replayed message, or left sending, is drafted as unknown), and leaves the requirements, the people's roles and the truth for the owner to write; an unidentified sender needs no role. It keeps each event's author, direction and body, not its kind, attachments, reply-to link or device: a schedule, a task result or a photo replays as a plain text message. A store that no process has open, as after serve stops, is read as immutable, since the system SQLite cannot open it read-only otherwise. `run` refuses a results folder that already holds anything, so no run overwrites another. It first runs a preflight on an instance of its own: the harness must read a memory note through the broker, or the run stops as a setup error. Then it gives each case a fresh instance at `read` access with the Claude harness, writes the history into its store in its recorded delivery states, delivers the message through `oppa serve` and the synthetic channel, stops every process that serve started, keeps the instance's evidence (serve's log, each `oppa` command's output, the attempt records under `runs/` and the Claude session records of its turns under `claude-harness*/`) as `<id>.evidence/`, and only then removes the instance and its Claude session records: if any of it cannot be copied, nothing is removed and the error names where the originals stay. A case whose setup fails is recorded ungraded in `<id>.json` and the run goes on to the next case. A turn that does not complete within five minutes of starting grades nothing and is not judged. Empty output fails; silence counts only on the model's explicit NO_REPLY. A case naming B-2 lists in `retrieves` what the turn must find, placed where only a lookup reaches it: more than 64 messages back, since each case's instance starts with an empty memory; B-2 fails unless a successful history or memory tool result in the turn's Claude session record holds each of them, whatever the reply says; when the prompt recorded there already held one, or no prompt was recorded, the case cannot show retrieval and B-2 is ungraded. The text must not be in the replayed message itself. A failed assertion fails every requirement the case names; a separate judge (`claude -p` on `claude-opus-5-5` with no tools, no saved session and none of the user's settings or instructions) sees each person's role, which messages a person sent from their own device, and each lookup with its arguments, and grades each requirement as pass, fail or not shown; a judge that cannot run, fails, runs out of its ten minutes or answers anything but a grade for each requirement leaves them ungraded, and what it wrote (exit code, stdout and stderr, as far as it got) is kept in the case's result as `judge_failure`. Each case's line on stdout carries the requested model and effort, the models the turn's session record shows answered, the attempt and read counts, assertions, each requirement's grade as the report counts it (a failed assertion fails it whatever the judge said) and timing. Exit codes: 0 every requirement of every case passed, 1 a failure (which wins over the rest), 2 a build or setup error of any kind, an incomplete turn, or a requirement ungraded or not shown. `report.md` in the results folder has one row per requirement from B-1 to B-10. Only the owner's message is replayed: a case cannot yet replay a turn an adult started.

The runner works with the system `python3` (3.9) and Homebrew's (3.14); tests/replay.rs runs every check under each of them it finds.

Cases and results hold private conversation text. Keep them in the instance's private `evals/` folder or the private home, never in this repository. Run with `TMPDIR` outside any Git checkout: `oppa init` refuses an instance inside one.

## Evidence

General drives retain each `oppa` invocation's command line, exit code, stdout and stderr in `<instance>/evidence/<feature>/`. General background-task drives require an instance with no external connectors.

Evidence you share, in a pull request say, describes what was observed: never paste transcripts, paths under the home directory or personal data.

## Cleanup

`oppa-verify cleanup` stops only the processes the helper started (it records their PIDs). It leaves the instance and its evidence in place. Never stop an `oppa` process by name: the owner may be running one.

## Report

For each feature driven: PASS, FAIL with the failed check and the evidence file, or BLOCKED with the reason. Wrong descriptions in a feature file are doc drift (fix the file); behavior the helper cannot drive is a harness gap (fix the helper); broken behavior is a product bug (report it, do not fix product code during verification).
